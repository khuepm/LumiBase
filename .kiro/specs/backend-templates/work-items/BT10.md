## Detailed acceptance criteria
### BT10-AC01 — No auto-upgrade

- [ ] Publish 1.1 while 1.0 is installed; schema/items/installation version remain unchanged without explicit upgrade.
- Verification/evidence: DB test; attach test name, exact command, commit SHA and actual result.

### BT10-AC02 — Additive upgrade

- [ ] Add nullable field via approved 1.1 plan; existing content and unrelated collections preserved; baseline advances only on success.
- Verification/evidence: DB integration; attach test name, exact command, commit SHA and actual result.

### BT10-AC03 — User drift

- [ ] User edits a managed field and desired version edits same field differently; emit three-way conflict with base/current/desired and no write.
- Verification/evidence: Planner fixtures; attach test name, exact command, commit SHA and actual result.

### BT10-AC04 — Destructive gate

- [ ] Removing populated field or changing type cannot apply with ordinary install approval; require separately reviewed migration and current approval.
- Verification/evidence: Security/migration tests; attach test name, exact command, commit SHA and actual result.

### BT10-AC05 — Seed isolation

- [ ] Schema upgrade defaults to no seed migration; user-edited seed records are not overwritten by new demo pack.
- Verification/evidence: Content preservation test; attach test name, exact command, commit SHA and actual result.

### BT10-AC06 — Rollback/retry

- [ ] Failure during upgrade leaves previous schema/baseline and content; successful retry applies once. Unsupported downgrade fails explicitly.
- Verification/evidence: Fault injection + retry; attach test name, exact command, commit SHA and actual result.
