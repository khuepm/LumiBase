# BT04 — Atomic backend instantiation and installation provenance

**Parent:** #900 · **Task:** BT04 · **Owner lane:** Backend/apply

**Depends on:** BT03

**Codebase mirror:** [.kiro/specs/backend-templates/work-items/BT04.md](https://github.com/khuepm/LumiBase/blob/feature/backend-templates-spec/.kiro/specs/backend-templates/work-items/BT04.md)

## Outcome and scope
Reuse ConfigImportService/SchemaService through transaction-bound services; add create-only enforcement rather than blindly calling merge. Install schema, relation definitions, optional seeds and provenance in one supported DB transaction. Require transactional capability, no non-transaction fallback. Lock target scope, recheck permissions/fingerprint, persist idempotency key bound to plan digest, emit audit/cache/outbox effects after commit.


## Implementation work breakdown
- [ ] BT04-W1: Expose transaction-bound schema application without non-transaction fallback; enforce create-only inside the lock.
- [ ] BT04-W2: Implement installation state/provenance and payload-bound idempotency; allocate and resolve schema before optional seed hook.
- [ ] BT04-W3: Defer cache/outbox effects until commit; recover after worker loss using durable completion and transaction outcome.

## Expected code touchpoints
config-import-service.ts transaction interface; schema-service.ts integration; installation service/store and audit/runtime adapters. These are planning boundaries, not exclusive file grants; coordinate shared changes and preserve unrelated work.

## Detailed acceptance criteria
### BT04-AC01 — Complete commit

- [ ] Apply a valid plan; all expected schema and installation provenance appear together with pinned digest, namespace and seed selection.
- Verification/evidence: Real PostgreSQL test; attach test name, exact command, commit SHA and actual result.

### BT04-AC02 — Fault injection

- [ ] Throw after collection, field, relation, seed and provenance writes separately; target schema/items match pre-install snapshot; no completed installation or external event remains.
- Verification/evidence: DB fault-injection matrix; attach test name, exact command, commit SHA and actual result.

### BT04-AC03 — Concurrency

- [ ] Submit 10 identical requests concurrently; exactly one installation and one set of resources results, all successful retries resolve same installation ID.
- Verification/evidence: Concurrent DB test; attach test name, exact command, commit SHA and actual result.

### BT04-AC04 — Key misuse

- [ ] Reuse idempotency key with another plan/site-bound payload; return IDEMPOTENCY_CONFLICT, never replay another result.
- Verification/evidence: API tests; attach test name, exact command, commit SHA and actual result.

### BT04-AC05 — Apply race

- [ ] Change schema or revoke authorization between preview and apply; lock-time recheck rejects stale/unauthorized plan before writes.
- Verification/evidence: Interleaving test; attach test name, exact command, commit SHA and actual result.

### BT04-AC06 — Crash recovery

- [ ] Crash after commit before response, then retry; return committed installation without duplicating rows/outbox events. Crash before commit permits clean retry.
- Verification/evidence: Recovery integration; attach test name, exact command, commit SHA and actual result.

### BT04-AC07 — Commit effects

- [ ] Cached schema refreshes after commit; rollback emits no success event; worker retry deduplicates outbox delivery as supported by existing contracts.
- Verification/evidence: Cache/outbox integration; attach test name, exact command, commit SHA and actual result.
