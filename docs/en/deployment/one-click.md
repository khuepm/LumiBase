# One-click deploys

Templates that take a fresh account on Render, Railway or Fly.io to the LumiBase
setup wizard: the CMS API **and** the Studio, served from one container on one
origin, with PostgreSQL and Redis wired in and the secrets generated for you.

| Platform | What you click or type | Manual steps left |
|----------|------------------------|-------------------|
| Render | The **Deploy to Render** button (`render.yaml`) | None before the wizard. |
| Railway | The LumiBase template, once it is published (`railway.json`, `docker/railway-template-variables.json`) | None before the wizard. The template itself is a one-time maintainer step — see [Railway](#railway). |
| Fly.io | `fly launch` with `fly.toml` | Create Postgres and Redis, set two secrets — four commands. Fly generates no secrets. |
| Cloudflare | No button | Not one-click today — see [Cloudflare](#cloudflare). |

All three container platforms run the published image `ghcr.io/khuepm/lumibase-cms`
(see [Hardened image](./docker.md#hardened-image)), so what you deploy is the
signed, scanned release, not a build from your copy of the repository.

## What every template sets up

| Variable | How it is provided |
|----------|--------------------|
| `JWT_SECRET`, `ENCRYPTION_KEY` | Generated by the platform (Render, Railway) or by you with `openssl` (Fly). Never stored in the repository. |
| `DATABASE_URL`, `REDIS_URL` | Wired from the platform's PostgreSQL and Redis. |
| `CORS_ALLOWED_ORIGINS` | Derived at boot from the platform's public URL (`RENDER_EXTERNAL_URL`, `RAILWAY_PUBLIC_DOMAIN`, `FLY_APP_NAME`) when unset. |
| `LUMIBASE_REQUIRE_SETUP_TOKEN` | `true`: the instance is on the internet before anyone sets it up, and without the token whoever reaches `/setup` first becomes the admin. |
| `DATABASE_SSL_MODE` | `disable`, because each template connects over the platform's own private network. Set it to `require` with an external database. |
| `NODE_ENV`, `LUMIBASE_ENV`, `LUMIBASE_RUNTIME`, `PORT` | `production`, `production`, `docker`, `1989`. |

Production refuses to start without `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`,
`ENCRYPTION_KEY` and `CORS_ALLOWED_ORIGINS`. The image entrypoint
(`docker/scripts/entrypoint.mjs`) checks them before it touches the database and
exits with the names of the missing ones.

**Not provisioned** by any template: S3-compatible media storage, Meilisearch and
imgproxy. The instance boots and setup completes without them — `/health` reports
`degraded` until they exist — but uploads, search and image transforms need their
variables (`S3_ENDPOINT`, `MEILISEARCH_HOST`, `IMGPROXY_URL`, …), see
[Environment variables](./environment-variables.md).

## After the deploy: the setup wizard

1. Open the service logs. Once the server answers, the entrypoint prints the URL:

   ```text
   [entrypoint] Setup is pending. Open https://<your-app>/setup to create the first admin account.
   ```

2. Copy the one-time token printed earlier in the same log:

   ```text
   [lumibase-cms] SETUP_TOKEN=<token>
   ```

3. Open `/setup`, paste the token, and create the first admin. The Studio then
   lives under the admin path you choose there.

The token is printed once. If the log line is gone, see
[First-run setup](./environment-variables.md#first-run-setup) for how to issue a
new one.

## Render

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/khuepm/lumibase)

The Blueprint `render.yaml` creates a web service from the published image, a
Render Postgres 16 database and a Render Key Value instance (`noeviction`, which
the job queues need), all reachable only over Render's private network.
`JWT_SECRET` and `ENCRYPTION_KEY` use `generateValue`.

Plans: the web service uses `starter` because a free instance spins down when
idle, and with it the scheduler and queue workers this process runs. Change
plans in the dashboard or in your copy of `render.yaml`.

## Railway

`railway.json` configures a service built from `docker/Dockerfile` with a
`/health` deploy check. A Railway **template** — the button that also creates
Postgres and Redis and generates the secrets — is composed in Railway's template
editor and published from a Railway account; it cannot be read from the
repository. Until it is published, a maintainer creates it once:

1. In the template editor, add the official **Postgres** and **Redis** services
   and a service named `lumibase` from the Docker image
   `ghcr.io/khuepm/lumibase-cms:<version>`, with a public domain.
2. Copy the variables from `docker/railway-template-variables.json`. They use
   Railway's `${{secret(…)}}` functions, so every deploy generates its own
   `JWT_SECRET` and `ENCRYPTION_KEY` (the recipe produces a valid AES-256 key;
   the repository's tests check it).
3. Publish, and add the template's button here and in the README.

To deploy without the template, create the same three services in a project and
set the same variables, generating the two secrets with `openssl` as for Fly.

## Fly.io

Fly has no deploy button, generates no secrets, and runs Postgres and Redis as
separate resources. From an empty directory:

```bash
fly launch --from https://github.com/khuepm/lumibase --no-deploy
fly postgres create --name <app>-db
fly postgres attach <app>-db             # sets the DATABASE_URL secret
fly redis create                          # prints a redis:// URL
fly secrets set REDIS_URL=<that URL> \
  JWT_SECRET="$(openssl rand -base64 48)" \
  ENCRYPTION_KEY="$(openssl rand -base64 32)"
fly deploy
```

With Fly Managed Postgres instead, set `DATABASE_URL` from its connection string
with `fly secrets set`, and if that string carries `sslmode=require`, also set
`DATABASE_SSL_MODE=require`.

`fly.toml` keeps one machine running (`auto_stop_machines = "off"`): a stopped
machine runs no scheduler or workers. It stops the app with `SIGTERM`, which the
server drains on; Fly's default `SIGINT` would end it mid-request. A deploy
without the secrets fails at once, naming them, before the database is touched.
`CORS_ALLOWED_ORIGINS` defaults to `https://<app>.fly.dev`; set it, or
`LUMIBASE_PUBLIC_URL`, when you add your own domain.

## Cloudflare

There is no Deploy to Cloudflare button for LumiBase yet, and adding one to this
repository would not work:

- The button deploys one Worker from one directory, and treats that directory as
  the root of the new repository. `apps/cms` depends on workspace packages that
  would not be there.
- The CMS needs PostgreSQL through Hyperdrive. A Hyperdrive configuration points
  at an existing database, so the database itself cannot come from the button.
- The top-level configuration in `apps/cms/wrangler.toml` is the local
  development profile (`LUMIBASE_DEV_AUTH = "true"`). Deploying it as-is would
  publish an instance with development authentication.
- The Studio is a separate Cloudflare Pages project on this target, and the
  button deploys Workers only.

Use the scripted path in [Cloudflare Workers](./cloudflare.md) instead. A
self-contained Worker template that a button can deploy is tracked as backlog
B211.

## Pin a version

Every template points at `latest`, which follows the newest release. For
production, pin the tag you tested (`ghcr.io/khuepm/lumibase-cms:2.0.0`) and
change it deliberately; see [Docker → Updating](./docker.md#updating).
