## Progress accepted at source level

The claimed lifetime now has an outer catch, DB suites use explicit skip gates, and touched-service failures have a durable failed state with an explicit reopen endpoint. These address substantial parts of the preceding review. Current CI is green. The following gaps prevent acceptance.

## P1 — crash recovery bypasses explicit verification

`approval-claim-sweeper.ts` still changes stale `deciding` records directly to `pending`. A process can die after a non-idempotent mutation but before finalizing the approval. After 15 minutes, ordinary approval can execute it again without the new failed→reopen recovery gate. Writing an activity warning does not enforce recovery. This contradicts the purpose of the newly added failed outcome.

Quarantine stale/ambiguous claims in a non-executable state and require explicit verified recovery. Add a mutation→crash→sweep→decide regression. Do not assume elapsed time proves the underlying timed-out handler stopped; JavaScript timeout does not cancel the handler.

## P1 — retry safety does not cover all side-effect paths

`ServiceTouchTracker` proxies six injected services, but `buildCoreSkills` also constructs services internally. For example `deploymentService()` constructs a real DeploymentService and `deploy_trigger` invokes it without passing through any of the proxies. An external deployment followed by an error can leave the tracker false, causing the approval to return to pending. The claim that every new skill is automatically protected is unsupported.

Also, after a successful mutation, an exception while persisting the legacy approval escapes to the outer catch, which still calls `releaseClaim` unconditionally. This again reoffers an uncertain execution. Track the execution phase durably or default uncertain failures to failed; instrument every write surface. Add tests for a deployment/provider failure and a post-mutation persistence failure. These findings are based on the inspected source, not a live deployment reproduction.

## P2 — recovery authorization and its audit are not atomic

The reopen route commits failed→pending before inserting `approval.reopened`. If the audit insert fails, the endpoint errors but the action is already executable again, without the required audit record. The sweeper has the same update-then-audit ordering. Make the transition and required audit atomic or use a durable outbox; test audit-write failure.
